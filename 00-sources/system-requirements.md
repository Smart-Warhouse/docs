## 1. النطاق والمتطلبات العامة

النظام يبني مخزناً مصغراً بمقياس 1:14 فيه 3 رافعات ذاتية (+1 احتياط) تنقل الباليتات بين الرفوف ومناطق الاستلام والشحن بدون تدخل بشري، تحت إشراف خادم مركزي ولوحة مراقبة. كل متطلب مرقّم (مثل FR-01) حتى يُربط باختبار في القسم 14. الأرقام هنا قيم تصميم مقترحة وتُعدّل بعد أول اختبار فعلي.

**أجزاء النظام:** الرافعة (ميكانيك + إلكترونيات + ESP32 + Jetson) · الخادم (Fleet Manager + WMS + API) · لوحة المراقبة · بيئة المخزن.

## 3. الإلكترونيات والطاقة

الطاقة من بطارية واحدة 2S2P (7.4V اسمي، 6.0–8.4V فعلي، 7000mAh) تتفرع لثلاثة مسارات منفصلة: Jetson عبر Boost 12V، 5V للمنطق عبر Buck، والمحركات عبر E-Stop.

### ميزانية الطاقة (تقدير تصميمي)

| الحمل | الجهد | متوسط | أقصى |
| --- | --- | --- | --- |
| Jetson Orin Nano Super | Boost 12V → DC jack (9–20V) | 7 W | 15 W (وضع MAXN أعلى — نمنعه) |
| LiDAR C1 | 5V من Jetson USB | 1.2 W | 1.5 W |
| ESP32-S3 + الحساسات + LED | 5V/3.3V | 1 W | 2 W |
| محرك الدفع | 7.4V | 4 W | 10 W |
| محرك الرفع + الإزاحة + التوجيه | 7.4V | 2 W | 8 W |
| **المجموع** |  | **≈ 15 W** | **≈ 36 W** |

بطارية 7.4V × 7Ah ≈ 52 Wh → ≈ 3 ساعات نظرياً بالمتوسط، و≥ 45 دقيقة مضمونة حتى بالحمل الأقصى (NFR-05).

### متطلبات الطاقة والتوصيل

| الرقم | المتطلب |

## 4. Firmware الـ ESP32-S3

Firmware مكتوب بـ C/C++ على ESP-IDF (أو PlatformIO + Arduino core) فوق FreeRTOS، ويفصل السلامة على Core 1 عن الاتصال على Core 0 حتى لا يؤخر أي بطء بالاتصال رد فعل الأمان.

### المهام (FreeRTOS Tasks)

| المهمة | Core | التردد | الأولوية | العمل |
| --- | --- | --- | --- | --- |
| safety\_task | 1 | 1 kHz | الأعلى | يقرأ E-Stop وLimit وآخر قيم ToF، يطبق حدود السرعة، يراقب Watchdog |
| motor\_pid\_task | 1 | 1 kHz | عالية | PID سرعة الدفع من AS5600، PID ارتفاع الشوكة من البوتنشيوميتر، سيرفو التوجيه |
| tof\_task | 1 | 50 Hz (لكل حساس) | عالية | يقرأ 6 حساسات VL53L1X عبر TCA9548A |
| imu\_task | 0 | 100 Hz | متوسطة | يقرأ MPU9250 ويشغّل فلتر Madgwick → اتجاه (Quaternion) |
| microros\_task | 0 | حسب الرسائل | متوسطة | يستقبل الأوامر وينشر البيانات (القسم 10) |
| status\_task | 0 | 10 Hz | منخفضة | INA219، حلقة LED، البازر |

### المتطلبات

| الرقم | المتطلب |
| --- | --- |
| FW-01 | استقبال `cmd_vel` (سرعة خطية v وزاوية ω) وتحويلها لسرعة عجلة + زاوية توجيه بنموذج Ackermann (الرافعة توجّه من العجلات الخلفية — يتأكد من ME-01) |
| FW-02 | حساب Odometry من AS5600 + زاوية التوجيه ونشره 50 Hz |
| FW-03 | PID السرعة: خطأ ثابت ≤ 5% واستقرار خلال ≤ 300 ms؛ المعاملات قابلة للتعديل عبر ROS parameter |
| FW-04 | PID الرفع: الوصول للارتفاع المطلوب بدقة ± 3 مم، والتوقف الفوري عند ضغط Limit |
| FW-05 | معايرة (Calibration) محفوظة بالـ NVS: البوتنشيوميتر (مم)، مركز السيرفو، انحياز IMU، نصف قطر العجلة |
| FW-06 | Watchdog: إذا ما وصل `cmd_vel` أو نبض من Jetson خلال 500 ms → تباطؤ حتى التوقف + حالة SAFE |
| FW-07 | منطق السلامة بالـ ToF يعمل مستقلاً عن Jetson (القسم 9) |
| FW-08 | آلة حالات: BOOT → IDLE → ACTIVE ↔ SLOW → STOP → SAFE / ESTOP؛ الخروج من ESTOP يحتاج أمر Reset صريح |
| FW-09 | تشغيل سليم بدون Jetson: الـ Firmware يشتغل وحده ويبقى متوقفاً بأمان |
| FW-10 | رسائل تشخيص (Diagnostics): أخطاء الحساسات، حالة كل ToF، حرارة المعالج، زمن كل دورة |
| FW-11 | تحديث Firmware عبر USB من Jetson (أو OTA عبر Wi-Fi كميزة إضافية) |
| FW-12 | معرّف فريد لكل رافعة (robot\_id) محفوظ بالـ NVS، نفس الـ Firmware لكل الرافعات |

المكتبات: micro\_ros\_platformio (أو micro\_ros\_espidf\_component)، VL53L1X (Pololu)، AS5600، MPU9250 + Madgwick، INA219، FastLED/RMT.

## 5. Jetson: النظام وROS 2

Jetson يشغّل JetPack 6 (Ubuntu 22.04) مع ROS 2 Humble، وكل وظيفة عقدة (Node) مستقلة تُشغّل من ملف Launch واحد مع Namespace لكل رافعة (`/fl1`, `/fl2`, `/fl3`).

| الرقم | المتطلب |
| --- | --- |
| JS-01 | تثبيت JetPack 6.x على NVMe (الإقلاع من NVMe لا microSD)، وضع الطاقة 15W عبر `nvpmodel` لتقليل الاستهلاك |
| JS-02 | ROS 2 Humble (ros-base) + Nav2 + slam\_toolbox + robot\_localization + rplidar\_ros (sllidar\_ros2) + micro-ROS Agent |
| JS-03 | كاميرا CSI عبر Argus/GStreamer → عقدة ROS تنشر `image_raw` 640×480 @ 30 fps؛ يجب التأكد أن Camera Module 3 (IMX708) مدعومة بدرايفر Jetson أو استبدالها بـ IMX219 أو كاميرا USB |
| JS-04 | TensorRT + ONNX Runtime-GPU لتشغيل YOLO وسياسة RL |
| JS-05 | كل الإعدادات بملفات YAML ضمن حزمة `forklift_bringup`؛ لا قيم ثابتة بالكود |
| JS-06 | شجرة TF كاملة: `map → odom → base_link → {laser, camera, imu, fork}` من ملف URDF للرافعة |
| JS-07 | تشغيل تلقائي عند الإقلاع عبر خدمة systemd |
| JS-08 | تسجيل rosbag لكل تجربة (الليدار، odom، cmd\_vel، الحالة) للتحليل وتحسين RL |
| JS-09 | استهلاك CPU ≤ 70% وذاكرة ≤ 6 GB أثناء التشغيل الكامل |
| JS-10 | التحقق هل كت Jetson يحتوي بطاقة Wi-Fi مثبتة؛ إذا لا → Intel AX210 على M.2 Key E |

### الحزم (ROS 2 Packages) التي نكتبها

| الحزمة | المحتوى |
| --- | --- |
| `forklift_description` | URDF/Xacro للرافعة (الأبعاد، أماكن الحساسات) |
| `forklift_bringup` | ملفات Launch والإعدادات YAML |
| `forklift_interfaces` | رسائل وخدمات وActions خاصة (Lift, Task, Status) |
| `forklift_perception` | ArUco، YOLO، تقدير موقع البالية |
| `forklift_navigation` | إعدادات Nav2 وslam\_toolbox وEKF |
| `forklift_mission` | Behavior Tree للمهمة + عميل الأسطول (MQTT) |
| `forklift_rl` | تشغيل سياسة RL بـ TensorRT |
| `forklift_safety` | مشرف الأمان (حد السرعة، إلغاء الأوامر الخطرة) |
| `forklift_sim` | عالم Gazebo للمخزن + نموذج الرافعة |

## 6. الإدراك (Perception)

موقع البالية يُحسب أساساً من علامة ArUco ملصوقة على وجهها (دقيق ومضمون)، وYOLO يكشف الأشخاص والباليات بدون علامة كطبقة ثانية.

| الرقم | المتطلب |
| --- | --- |
| PC-01 | معايرة الكاميرا (Intrinsics) بلوح شطرنج عبر `camera_calibration`؛ خطأ إعادة الإسقاط ≤ 0.5 بكسل |
| PC-02 | معايرة الموضع (Extrinsics) بين الكاميرا والليدار و`base_link` وتثبيتها بالـ URDF |
| PC-03 | علامات ArUco: قاموس `DICT_4X4_50`، مقاس 30 مم للباليات و 60 مم للرفوف ونقاط التمركز؛ الأرقام 1–20 باليات، 21–40 مواقع |
| PC-04 | كشف ArUco وتقدير موقعها الثلاثي (solvePnP) بـ ≥ 20 Hz؛ دقة ≤ 1 سم و ≤ 2° على مسافة ≤ 50 سم |
| PC-05 | نشر `pallet_pose` (PoseStamped بإطار `map`) مع مؤشر ثقة؛ فلترة بمتوسط متحرك لآخر 5 قراءات |
| PC-06 | YOLO (v8n أو v11n) بفئات: `person` · `pallet` · `forklift` · `obstacle`؛ مدخل 640×640، TensorRT FP16 |
| PC-07 | زمن استدلال YOLO ≤ 30 ms للصورة على Jetson، معدل ≥ 15 fps |
| PC-08 | دقة YOLO: mAP@0.5 ≥ 0.85 على مجموعة اختبار، وRecall للـ `person` ≥ 0.95 (أولوية الأمان) |
| PC-09 | الليدار: تشغيل `sllidar_ros2` بـ 10 Hz، قص النقاط التي تضرب هيكل الرافعة نفسه (الصاري والأعمدة) عبر `laser_filters` |
| PC-10 | كشف العوائق الجديدة من الليدار (غير موجودة بالخريطة) وإضافتها للـ Costmap |
| PC-11 | إضاءة المخزن منتظمة ≥ 300 lux؛ النظام يُختبر بـ 3 مستويات إضاءة |

**بيانات تدريب YOLO:** ≥ 400 صورة لكل فئة من نفس كاميرا الرافعة بالمخزن المصغر (زوايا ومسافات وإضاءة مختلفة)، توسيم بـ Roboflow أو CVAT، تقسيم 70/20/10. الـ `person` بالنموذج المصغر يُمثّل بدمى بمقياس 1:14 + أقدام أشخاص حقيقية.

## 7. الخريطة وتحديد الموقع والملاحة

الخريطة تُرسم مرة واحدة بـ slam\_toolbox وتُشارك بين الرافعات الثلاث، وكل رافعة تحدد موقعها عليها وتخطط مسارها بـ Nav2 مع نموذج حركة Ackermann. الاقتراب النهائي من البالية (آخر ≈ 40 سم) ليس من Nav2 بل من وحدة الالتقاط (القسم 8).

| الرقم | المتطلب |
| --- | --- |
| NV-01 | رسم خريطة المخزن بـ slam\_toolbox (وضع Mapping)، دقة الخلية 2 سم، حفظها (`.pgm` + `.yaml` + serialized) ونشرها للخادم |
| NV-02 | تحديد الموقع على الخريطة الثابتة (slam\_toolbox Localization أو AMCL)؛ خطأ ≤ 3 سم (NFR-01) |
| NV-03 | EKF (robot\_localization) يدمج odom العجلات + IMU بـ 50 Hz → `odom → base_link` |
| NV-04 | تحديد الموقع الابتدائي تلقائياً من علامة ArUco مثبتة بمنطقة الشحن (بدل 2D Pose Estimate اليدوي) |
| NV-05 | مخطط المسار العام: Smac Planner Hybrid-A\* (يحترم أقل نصف قطر دوران الرافعة + الرجوع للخلف) |
| NV-06 | المتحكم المحلي: Regulated Pure Pursuit (أو MPPI بنموذج Ackermann)، 20 Hz، تباطؤ تلقائي بالمنعطفات وقرب العوائق |
| NV-07 | Costmaps: طبقة ثابتة (الخريطة) + عوائق (الليدار) + Inflation بنصف قطر ≥ نصف عرض الرافعة + 3 سم |
| NV-08 | مناطق ممنوعة (Keepout) ومناطق سرعة محدودة (Speed Filter) من طبقة Filter Mask بـ Nav2 |
| NV-09 | استخدام شبكة ممرات ثابتة (Waypoint graph) يحددها الخادم حتى ينظم المرور بين الرافعات (FR-08) |
| NV-10 | سلوكيات التعافي (Recovery): توقف وانتظار، رجوع بسيط، إعادة تخطيط؛ بعد 3 محاولات فاشلة إبلاغ الخادم |
| NV-11 | الوصول للهدف: تسامح موقع 5 سم واتجاه 5° (الدقة النهائية تأتي من وحدة الالتقاط) |
| NV-12 | أبعاد الرافعة (Footprint) مضلع حقيقي يشمل الشوك ويتغير عند حمل بالية |

## 8. الذكاء الاصطناعي: الالتقاط بـ RL وتوزيع المهام

سياسة RL تتحكم فقط بالاقتراب النهائي من البالية وإدخال الشوكة، وقبلها يُبنى متحكم كلاسيكي (Visual Servoing من ArUco) كمرجع يجب أن تتفوق عليه السياسة. هذا يضمن أن المشروع يعمل حتى لو تأخر RL.

### مهمة الالتقاط (Pallet Docking)

| العنصر | التعريف |
| --- | --- |
| البداية | الرافعة على بعد 30–60 سم من البالية، انحراف جانبي ± 10 سم، زاوية ± 20° |
| الملاحظة (Observation) | موقع البالية النسبي (dx, dy, dθ) من ArUco · السرعة الحالية · زاوية التوجيه · ارتفاع الشوكة · قراءات ToF الأمامية · حالة TCRT5000 |
| الفعل (Action) | سرعة خطية \[-0.1, 0.1\] م/ث · زاوية توجيه \[-30°, 30°\] · تغيير ارتفاع الشوكة |
| المكافأة (Reward) | + للاقتراب وتقليل الانحراف · +100 للإدخال الكامل (TCRT الاثنين) · −100 للاصطدام · عقوبة صغيرة لكل خطوة وللتغيير المفاجئ بالتوجيه |
| النجاح | الشوكتان داخل الفتحتين ≥ 80% من طولهما بدون لمس وانحراف ≤ 1 سم |

### المتطلبات

| الرقم | المتطلب |
| --- | --- |
| AI-01 | محاكي بنموذج الرافعة والبالية بالأبعاد الحقيقية: Gazebo (Harmonic) للنظام الكامل، وبيئة Gymnasium خفيفة (أو Isaac Lab إذا توفر GPU RTX) للتدريب السريع |
| AI-02 | خوارزمية PPO (Stable-Baselines3 أو RSL-RL)، ≥ 2 مليون خطوة، مع حفظ النقاط (Checkpoints) ومنحنى التدريب بـ TensorBoard |
| AI-03 | Domain Randomization: احتكاك، تأخير المحرك 20–80 ms، ضوضاء على موقع ArUco ± 5 مم، وزن وموضع البالية |
| AI-04 | نجاح ≥ 95% بالمحاكي على 1000 حالة عشوائية قبل النقل للواقع |
| AI-05 | تصدير ONNX → TensorRT FP16 على Jetson؛ زمن الاستدلال ≤ 5 ms، التشغيل 20 Hz |
| AI-06 | كل أمر من السياسة يمر عبر مشرف الأمان (حد سرعة 0.1 م/ث، ToF) قبل ESP32 |
| AI-07 | المقارنة بالواقع: 30 محاولة RL مقابل 30 محاولة بالمتحكم الكلاسيكي؛ المقياس: نسبة النجاح، الزمن، خطأ الانحراف |
| AI-08 | توزيع المهام بالخادم: النسخة الأولى قاعدة بسيطة (الأقرب + بطارية كافية)، ثم تحسين (Hungarian algorithm) أو RL متعدد الوكلاء كميزة متقدمة؛ يُقارن بمتوسط زمن إنجاز المهمة |
| AI-09 | ملف نموذج مرقّم بإصدار (v1, v2…) مع تاريخ التدريب ونتيجة التقييم، وإمكانية الرجوع للنسخة السابقة |

حاسوب التدريب: لابتوب بـ GPU NVIDIA أو Google Colab؛ Jetson للتشغيل فقط لا للتدريب.

## 9. متطلبات السلامة

السلامة مبنية من طبقات مستقلة، كل واحدة تعمل لو فشلت التي فوقها: الأجهزة (E-Stop) ثم ESP32 (ToF + Watchdog) ثم Jetson (Nav2 + YOLO + مشرف الأمان) ثم الخادم.

| الرقم | المتطلب | الطبقة |
| --- | --- | --- |
| SF-01 | ضغط E-Stop يقطع طاقة كل المحركات فوراً بدون برمجيات | الأجهزة |
| SF-02 | حلقة ToF: مسافة < 40 سم → تحديد السرعة 30%؛ < 15 سم → توقف كامل (باتجاه الحركة فقط) | ESP32 |
| SF-03 | أثناء الالتقاط تُعطّل الحساسات الأمامية التي ترى البالية نفسها فقط، وتبقى السرعة ≤ 0.1 م/ث | ESP32 + Jetson |
| SF-04 | Watchdog: انقطاع Jetson > 500 ms → توقف | ESP32 |
| SF-05 | انقطاع Wi-Fi بالخادم > 3 ث → إكمال المقطع الحالي بأمان ثم التوقف والانتظار | Jetson |
| SF-06 | كشف شخص (YOLO) ضمن 1 م من المسار → تباطؤ أو توقف | Jetson |
| SF-07 | المشرف يفرض الحدود على كل الأوامر (Nav2 وRL وGamepad): السرعة، التسارع، السرعة بحمل مرفوع | Jetson |

## 10. الاتصال والواجهات

داخل الرافعة كل شي ROS 2 (micro-ROS بين ESP32 وJetson عبر USB)، وبين الرافعة والخادم MQTT برسائل JSON على Wi-Fi حتى يبقى الخادم مستقلاً عن ROS.

### ESP32 ↔ Jetson (micro-ROS)

| Topic | النوع | الاتجاه | التردد |
| --- | --- | --- | --- |
| `cmd_vel` | geometry\_msgs/Twist | Jetson → ESP32 | 20 Hz |
| `lift_cmd` | std\_msgs/Float32 (ارتفاع مم) | Jetson → ESP32 | عند الطلب |
| `sideshift_cmd` | std\_msgs/Int8 (−1/0/1) | Jetson → ESP32 | عند الطلب |
| `heartbeat` | std\_msgs/UInt32 | Jetson → ESP32 | 10 Hz |
| `wheel_odom` | nav\_msgs/Odometry | ESP32 → Jetson | 50 Hz |
| `imu/data` | sensor\_msgs/Imu | ESP32 → Jetson | 100 Hz |
| `tof_ring` | std\_msgs/Float32MultiArray (6 مسافات) | ESP32 → Jetson | 20 Hz |
| `fork_state` | رسالة خاصة (ارتفاع، Limits، TCRT) | ESP32 → Jetson | 20 Hz |
| `battery` | sensor\_msgs/BatteryState | ESP32 → Jetson | 1 Hz |
| `safety_state` | std\_msgs/UInt8 (الحالة + السبب) | ESP32 → Jetson | 10 Hz + عند التغير |

### الرافعة ↔ الخادم (MQTT)

| Topic | الاتجاه | QoS | المحتوى |
| --- | --- | --- | --- |
| `wh/fl/{id}/state` | رافعة → خادم | 0 · 2 Hz | الموقع، السرعة، البطارية، الوضع، حمل بالية |
| `wh/fl/{id}/task` | خادم → رافعة | 1 | مهمة جديدة (المصدر، الوجهة، البالية، المسار) |
| `wh/fl/{id}/task_status` | رافعة → خادم | 1 | مرحلة المهمة: accepted / to\_pickup / picking / to\_drop / done / failed |
| `wh/fl/{id}/cmd` | خادم → رافعة | 1 | pause / resume / cancel / go\_charge / reset |
| `wh/fl/{id}/event` | رافعة → خادم | 1 | أحداث أمان وأخطاء |
| `wh/traffic/{segment}` | خادم ↔ رافعة | 1 | طلب ومنح وتحرير مقطع ممر |
| `wh/fleet/estop` | خادم → الكل | 1 · retained | إيقاف الأسطول كله |

مثال رسالة مهمة:

```json
{
  "task_id": "T-0042",
  "type": "move_pallet",
  "pallet_id": 7,
  "from": {"location": "R1-L2", "x": 1.20, "y": 0.45, "yaw": 1.57, "height_mm": 60},
  "to": {"location": "DOCK-1", "x": 0.30, "y": 1.80, "yaw": 3.14, "height_mm": 0},
  "route": ["N3", "N4", "N7"],
  "priority": 2,
  "issued_at": "2026-10-16T19:50:00Z"
}
```

| الرقم | المتطلب |
| --- | --- |
| CM-01 | Broker محلي Mosquitto على الخادم، بمصادقة اسم مستخدم/كلمة مرور لكل رافعة |
| CM-02 | راوتر Wi-Fi مخصص (5 GHz) للمشروع، IP ثابت لكل رافعة وللخادم |
| CM-03 | رسالة Last Will لكل رافعة حتى يعرف الخادم فوراً بانقطاعها |
| CM-04 | كل رسالة فيها طابع زمني ورقم تسلسلي؛ مزامنة الساعة بـ NTP/chrony |
| CM-05 | توثيق كل الرسائل بـ JSON Schema داخل المستودع |

## 15. أدوات التطوير والخطة المرحلية

العمل مقسم لـ 6 مراحل، وكل مرحلة ما تبدأ إلا بعد نجاح اختبارات المرحلة السابقة (القسم 14)، حتى لا تتراكم أخطاء المراحل الأولى.
